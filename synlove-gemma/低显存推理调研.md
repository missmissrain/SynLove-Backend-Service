# 低显存推理方案调研（GTX 1060 6G / i5-9400F / 16G）

> 目标机器：Win10 + GTX 1060 6GB（Pascal）+ i5-9400F（6 核 6 线程）+ 16GB DDR4。
> 要跑的东西：Gemma 4 E4B（Q4_K_M，含视觉投影器）+ Breeze-TTS-2（7.13GB 权重）+ Whisper。
>
> 结论放在最前面：
> 1. **Gemma 走「量化 + 部分卸载（`-ngl`）」**，不要用逐层加载；
> 2. **Breeze-TTS-2 在 1060 6G 上跑不动** —— 它的权重 7.13GB、eager 推理要 7.7GB 显存，
>    连主干（不加音频分词器）都有 6.49GB。这台机器上 TTS 只有三条路：换小模型 / 8bit 量化 / 换机器跑；
> 3. 逐层加载（AirLLM 那一类）对 TTS **完全无效**，原因见第 4.2 节。

---

## 1. 先算清楚账：到底差多少显存

按仓库里 `下载校验.json` 的实际文件大小：

| 文件 | 字节 | 折算 |
| --- | --- | --- |
| `gemma-4-E4B-it-Q4_K_M.gguf` | 4 977 171 584 | **4.64 GiB** |
| `mmproj-BF16.gguf`（视觉投影器） | 991 552 320 | **0.92 GiB** |
| 合计 | — | **5.56 GiB** |

GTX 1060 标称 6144 MiB，但 Windows 下真实可用只有 **5.0~5.3 GiB**（驱动 + 桌面窗口管理器要占
0.6~1.0 GiB，开着浏览器还会更多）。再减去 KV cache 与计算缓冲：

| 上下文长度 | KV cache（E4B 量级，fp16） | 计算缓冲 | 合计需求 |
| --- | --- | --- | --- |
| 2048 | 约 0.2~0.4 GiB | 约 0.3 GiB | 6.1~6.4 GiB（超了） |
| 4096 | 约 0.4~0.8 GiB | 约 0.4 GiB | 6.4~6.8 GiB（超更多） |

**结论**：带视觉投影器，1060 6G 装不下；去掉投影器（只做纯文本）也只是「勉强、且不能开大上下文」。
所以这台机器**确实需要把一部分层放到 CPU 上算**。

## 2. 四条技术路线，各自的真实代价

### 2.1 量化 + 部分卸载（llama.cpp `-ngl`）——生产可用，推荐

**做法**：把模型的 N 层放显存、剩下的层留在内存里用 CPU 算。前向传播时 GPU 算完自己那几层，
把中间激活（几十 KB 级别）传给 CPU 接着算。**权重放哪就一直在哪，每个 token 不用搬。**

llama.cpp / llama-server 里的开关：

| 参数 | 作用 |
| --- | --- |
| `-ngl N` / `--n-gpu-layers N` | 放 N 层到 GPU；`-ngl 999` 是「能放多少放多少」 |
| `--no-kv-offload` | KV cache 不占显存（放到内存），省几百 MB |
| `-c 2048` | 上下文调小，直接省 KV cache |
| `--no-mmap` / mmap | 默认用 mmap，让 OS 页缓存帮你兜底 |
| `-fa on/off` | flash attention；Pascal 上收益有限，显存紧张时可以试 |

**代价**：CPU 那部分层用的是 DDR4-2666 双通道（理论 41.6 GB/s，实测 25~30 GB/s），
比 1060 的 192 GB/s 慢 6~7 倍。所以卸载的层越多越慢，但**是线性变慢**，不是数量级崩塌。

粗算（E4B Q4，4.64 GiB）：

| 卸载比例 | 大致速度 | 适用 |
| --- | --- | --- |
| 0%（全 GPU，不可能，装不下） | — | — |
| 10~20% 放 CPU（约 0.5~1 GB） | 约 12~18 token/s | 日常聊天完全够 |
| 50% 放 CPU | 约 5~8 token/s | 还能用，长回答会明显等 |
| 100% 纯 CPU | 约 3~5 token/s | 兜底 |

> 上表是按带宽估的量级，真值必须实测（见第 6 节）。

### 2.2 逐层加载 / 权重流式（AirLLM 派）——能跑巨大模型，但慢两个数量级

**做法**（就是用户说的那个算法）：把模型按层切成 shard 存到磁盘，推理时**只把当前这一层搬进显存**，
算完立刻释放，再搬下一层；配上分块量化（4bit/8bit）把要搬的字节数压小，再加 prefetch 把
「搬下一层」和「算这一层」重叠起来。

代表实现：**AirLLM**（github.com/lyogavin/airllm，41k star，Apache-2.0）。
官方说法是「GPU 上永远只有一层，所以显存需求取决于单层大小，而不是模型总大小」，
能在 4GB 卡上跑 70B、在 ~12GB 上跑 DeepSeek-V3 671B；v2.0 加的分块量化号称提速 3 倍。

**为什么在你这台机器上不划算**：它成立的前提是「模型大到没法用别的手段」。代价是
**每生成一个 token，都要把整个模型从存储里读一遍**。按 1060/PCIe 3.0 的实际情况：

| 存储 | 顺序读带宽 | 4.64 GiB 模型读一遍 | 理论 token/s |
| --- | --- | --- | --- |
| SATA SSD | 约 0.5 GB/s | 约 9.3 s | **0.1** |
| NVMe SSD（PCIe 3.0 x4） | 约 3.0 GB/s | 约 1.6 s | **0.6** |
| 全在内存页缓存（16GB 勉强够） | 约 10 GB/s | 约 0.46 s | **2** |

也就是说，即便模型能整个塞进系统内存、完全不碰磁盘，也就 2 token/s 量级；
一句 30 字的回复要等半分钟以上。**拿来离线批处理（夜里生成摘要、整理日志）可以，交互式对话不行。**

而且 AirLLM 还有个副作用：第一次要先把 HuggingFace 权重「按层切分」落盘，**磁盘占用翻倍**，
16GB 内存的机器上切一个 4.6GB 模型会明显卡（官方 FAQ 里 `MetadataIncompleteBuffer` 报错
最常见的原因就是磁盘不够）。

### 2.3 CPU/GPU 神经元级混合（PowerInfer）——论文很漂亮，生态很薄

**做法**：利用 LLM 激活的「幂律分布」——少数热神经元几乎每次都激活，多数冷神经元随输入变化。
把热神经元常驻显存、冷神经元放到 CPU 上算，再配一个预测器提前知道哪些神经元会被激活。

论文：*PowerInfer: Fast Large Language Model Serving with a Consumer-grade GPU*（SOSP 2024，
arXiv:2312.12456）。摘要里的数字：在单张 RTX 4090 上比 llama.cpp 快最多 **11.69×**；
OPT-30B 能跑到 A100 的 82% 生成速度。

**问题**：需要针对具体模型离线做「热/冷神经元」profiling，仓库支持的模型有限，
Windows 上编译 CUDA + 自定义稀疏算子很折腾。**不建议在 1060 上走这条路**，除非以后专门为某个
固定模型做优化。

### 2.4 多级存储调度（FlexGen）——高吞吐，不是低延迟

**做法**：把权重和 KV cache 在 GPU / CPU / 磁盘三级之间调度，用线性规划搜最优的
「放哪、什么粒度搬、batch 多大」，权重和 KV 都压到 4bit。

论文：*FlexGen: High-Throughput Generative Inference of Large Language Models with a Single GPU*
（arXiv:2303.06865）。摘要明确说是面向「**latency-insensitive tasks with batched processing**」：
OPT-175B 在单张 16GB 卡上，用有效 batch 144 达到 **1 token/s**。

注意这句话的含义：1 token/s 是**整批 144 个序列合起来**的吞吐，单条序列的延迟非常难看。
家庭管家是「一句话进去、一句话出来」的交互场景，**FlexGen 的优化目标和我们相反**。

## 3. 所以到底该选哪条

| 场景 | 选什么 | 理由 |
| --- | --- | --- |
| E4B 纯文本，日常对话 | **llama.cpp + `-ngl` 部分卸载**（10~20% 层给 CPU） | 12~18 token/s，改动最小，一条命令 |
| E4B 带视觉（要 mmproj） | 同上，但把 mmproj 放 CPU（`--no-mmproj-offload`）或干脆降到 Q3 | 0.92 GiB 投影器放显存代价太大 |
| 想跑 12B~14B | 部分卸载 50% 左右，5~8 token/s | 能跑，但长回答会等 |
| 夜里跑批处理（写日报、整理记录） | **AirLLM** 或直接纯 CPU | 不在乎延迟，只在乎能不能跑 |
| 批量压测/离线评测 | FlexGen | 吞吐优先 |
| **Breeze-TTS-2（7.13GB）** | **换机器跑（路线 C）或换小模型（路线 A）** | 1060 6G 装不下，int8 量化是唯一原地办法但音质待验 |

**给这台的推荐配置（草案）**：

```bat
llama-server.exe ^
  --model model\gemma-4-E4B-it-Q4_K_M.gguf ^
  --mmproj model\mmproj-BF16.gguf ^
  --n-gpu-layers 24 ^
  --no-mmproj-offload ^
  --ctx-size 2048 ^
  --no-kv-offload ^
  --flash-attn off ^
  --host 127.0.0.1 --port 8080
```

`-ngl 24` 只是起点，要按实测往上加，加到「显存还剩 300~500MiB」为止。

## 4. TTS：这才是真正过不去的那道坎

### 4.1 先摆事实：Breeze-TTS-2 有多大

按 `synlove-tts/README.md` 里的权重清单：

| 文件 | 字节 | 折算 |
| --- | --- | --- |
| `model-00001-of-00002.safetensors` | 4 961 989 890 | 4.62 GiB |
| `model-00002-of-00002.safetensors` | 2 004 567 152 | 1.87 GiB |
| `audio_tokenizer/model.safetensors` | 682 293 092 | 0.64 GiB |
| **合计** | | **7.13 GiB** |

反推参数量：7.13GB ÷ 2 字节（bf16/fp16）≈ **3.5B 参数**。这不是「小 TTS」，
它已经和 Gemma E4B 是一个量级，甚至更大。

而 `synlove-tts/README.md` 自己写得很清楚：

> **不常驻**：权重 7GB、eager 推理 **7.7GB 显存**，8GB 卡上常驻会挤死对话模型
> **显存 < 6GB 的卡不建议用**（会频繁等显存）
> `BREEZE_NEED_VRAM_MB` 默认 **6500**

所以准确的结论是：**1060 6G 根本装不下 Breeze-TTS-2**，不是「挤一挤能跑」。
连主干（4.62 + 1.87 = **6.49 GiB**，不含音频分词器）都超过 1060 的 5.0~5.3 GiB 可用显存。

### 4.2 为什么「逐层推理」对 TTS 无效

TTS 和 LLM 的生成方式不同，这决定了逐层加载在这里的代价：

- **自回归 TTS**（先出 audio token、再解码成波形）：一段 5 秒语音大约是几千个 audio token，
  **每个 token 都要跑一遍完整网络**。逐层加载意味着每个 token 搬 7GB →
  按 NVMe 3GB/s 算，一个 token 2.3 秒，一句话要从天亮等到天黑。
- **扩散 / 流匹配 TTS**：每次合成要迭代几十步，**每步都是一次完整前向**，同样灾难。
- LLM 至少还能靠「一个 token 一次前向」勉强撑住 1~2 token/s，TTS 连这个都做不到。

**唯一有意义的分层是「按组件切」，不是「按层切」**：text encoder → 主干 → audio tokenizer →
vocoder，逐个载入、用完释放，峰值显存 = 最大的那个组件。但对 Breeze-TTS-2 来说，
最大的组件就是 6.49GB 的主干本身，**切了也没用**。

### 4.3 三条可行的路（按推荐度）

**路线 A：换更小的 TTS（最推荐）**

TTS 的音质和参数量不是线性关系。300M~1B 级别的模型在中文女声上已经相当自然：

| 方案 | 大致权重 | 6G 卡可行性 |
| --- | --- | --- |
| Kokoro（82M） | 约 0.3GB | 轻松，还能常驻 |
| CosyVoice2（0.5B） | 约 1~2GB | 可以常驻 |
| GPT-SoVITS v2 | 约 0.7GB | 轻松，且支持音色克隆 |
| 现有 Breeze-TTS-2（3.5B） | 7.13GB | **装不下** |

代价是音色细节、情感控制会比 3.5B 的略差，但「能一直用」比「音质好一点但跑不起来」重要。

**路线 B：给 Breeze-TTS-2 做 8bit 量化（能做，但要实测音质）**

- fp16 → int8：约 3.3GB，加音频分词器 0.64GB ≈ 4GB，能塞进 6G（留出计算缓冲）；
- 风险：TTS 对量化比 LLM 敏感，尤其扩散/流匹配结构，容易出现齿音、气声失真、音高抖动；
- 上游代码是否支持要确认（`bitsandbytes` 在 Windows + CUDA 12 可用，但需要改加载路径）。

**路线 C：让另一台机器跑 TTS（架构上最优雅）**

整条链路是**串行**的：说话 → ASR → LLM → TTS。同一时刻只需要一个大模型占显存。
而消息中转框架本来就是**按能力路由到不同机器**的：

```
台式机（1060 6G）：chat（Gemma，部分卸载）+ asr（Whisper）
笔记本（4070 8G）：tts（Breeze-TTS-2，7.7GB 刚好够）
        ↓ 都主动外连
      VPS Hub：按能力派单
```

调用方只写 `capability: "tts"`，根本不知道它在哪台机器上跑。
**这条路不用改任何算法，只需要在两台机器上各起一个节点。**

### 4.4 顺带说一句 Whisper

Whisper base/small 是几十到几百 MB，1060 上随便跑，甚至可以 CPU。这一环不用操心。

## 5. Windows + Pascal 特有的坑（这部分比算法更容易踩）

1. **WDDM 的「共享 GPU 内存」是陷阱**。任务管理器会显示「专用 6GB + 共享 8GB」，看起来能用 14GB，
   其实超出专用显存的部分要走 PCIe 借系统内存，速度断崖式下跌（可能掉到 1/5）。
   **判断标准：只看「专用 GPU 内存」占用，永远给它留 300~500MB 余量。**
2. **CUDA 12.x 是最后支持 Pascal 的大版本**，CUDA 13 起官方不再支持 Maxwell/Pascal/Volta。
   别去装最新 toolkit，用 llama.cpp 的 `cu12` 预编译包或者自己按 CUDA 12 编译。
3. **1060 没有 Tensor Core，FP16 算力被砍到 1/64**。所以「FP16 比 Q4 快」在 Pascal 上不成立，
   Q4_K_M 这类整数量化反而是对的；也不用指望 flash-attention 的加速。
4. **16GB 内存跑 offload 容易触发页面文件抖动**。跑之前关掉浏览器和 WeChat 之类的大户，
   保证有 10GB 以上空闲物理内存。
5. **mmap 是双刃剑**：默认开，好处是 OS 页缓存能复用权重；坏处是内存压力大时会反复缺页。
   内存吃紧时试 `--no-mmap`。

## 6. 实测：交替放置 + 双缓冲到底能赚多少

用户提出的方案（`layerPipelineExp/`，已实现并跑通）：

> 头两层载入显卡，后两层留在 CPU，再后两层轮转到显卡；CPU 计算时 GPU 做 IO，
> CPU 算完显卡正好接上。

实现在 `layerPipeline.py`：静态交替放置 + 两个 GPU 槽位双缓冲，权重先 `pin_memory()`，
复制走独立 CUDA stream，计算流用 event 等它。

**实测（RTX 4070 Laptop 8G，PCIe 4.0 x8，12 个 192MB 的块，显存预算 1.2GB）：**

| 模式 | token/s | 每 token 耗时 | 每 token 搬运 |
| --- | --- | --- | --- |
| partial（超出部分留 CPU，等价 `-ngl`） | **14.96** | 66.8 ms | 0 MB |
| pipeline（交替 + 双缓冲） | 12.79 | 78.2 ms | 768 MB |
| serial（朴素逐层载入） | 1.99 | 503.6 ms | 768 MB |

- **流水线 vs 朴素逐层载入：6.44×** —— 重叠是实打实有效的；
- **流水线 vs 直接留 CPU：0.86×** —— 仍然慢 14%。

原因就一个算术：单块搬运 **17.9 ms**，单块 CPU 计算 **8.0 ms**，**搬运比计算贵 2.2 倍**。
重叠只能把「计算」藏进「搬运」，但藏不掉搬运本身。所以：
**只要权重还在内存里、还能用 CPU 算，就不该为了「用上 GPU 的算力」而搬它** ——
单 token 生成是内存带宽受限的，GPU 那 0.4ms 的算力完全用不上。

### 6.1 什么时候这个方案才真的赚

| 场景 | 朴素做法 | 流水线 | 收益 |
| --- | --- | --- | --- |
| 权重在内存，逐 token 生成 | CPU 算 8ms | 搬 18ms | **亏**（本例） |
| 权重在磁盘（模型 > 内存），逐 token | 读 55ms + 算 8ms = 63ms | 读 55ms（算藏在读里） | **约 1.15×** |
| prompt 预填充（几百 token 一起算） | GPU 算力被放大几十倍 | 搬运占比变小 | **开始划算** |

结论：
1. **Gemma E4B 在 6G 卡上，正确解法是 `-ngl` 部分卸载**（本例的 partial，14.96 token/s）；
2. 用户这套流水线最适合的场景是「模型比内存还大、必须从磁盘流式」——那才是 AirLLM 的战场，
   此时它的价值是把「读 + 算」串行变成「读时算」；
3. 真正值得做的下一步不是继续抠搬运，而是 **prefill / decode 分离调度**：
   预填充阶段把层搬上 GPU（那时候换算力），生成阶段搬回 CPU（那时候省搬运）。

## 7. 下一步的实验计划（必须实测，不能只看估算）


工具：`llama-bench`（llama.cpp 自带）或者直接 `llama-server` + 计时。

```
# 1) 纯 CPU 基线（-ngl 0）
llama-bench -m model\gemma-4-E4B-it-Q4_K_M.gguf -ngl 0 -p 64 -n 64

# 2) 阶梯加层：8 / 16 / 24 / 28 / 32 / 999，每档记 pp（预填充）和 tg（生成）速度
llama-bench -m model\gemma-4-E4B-it-Q4_K_M.gguf -ngl 24 -p 64 -n 64

# 3) 找到「显存还剩 300MB」的那一档，就是最优点
nvidia-smi --query-gpu=memory.used --format=csv -l 1
```

要记录的表（每档一行）：

| -ngl | 专用显存峰值 | pp tok/s | tg tok/s | 备注 |
| --- | --- | --- | --- | --- |

判定标准：
- **tg ≥ 8 token/s**：日常聊天可用；
- **tg 3~8**：只能接受短回复；
- **tg < 3**：换更小的模型（E2B / 4B 级别）比硬撑更划算。

> 注意：这一步必须在**目标机器（1060）**上做。当前开发机是 RTX 4070 Laptop 8GB，
> 上面的数字不能直接套用到 1060 上。
